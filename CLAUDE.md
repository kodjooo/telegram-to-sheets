Инструкции для AI-агента

Этот файл - точка входа для Codex и других AI-агентов, работающих с проектом Sellerdata. Перед изменениями обязательно прочитать:

- `ai-docs/arch-rules.md` - обязательные правила разработки и проверки изменений.
- `ai-docs/architecture.md` - актуальное описание архитектуры, доменных потоков и важных проектных решений.
- `ai-docs/database-structure.md` - структура БД (таблицы, связи, enum-значения). Точка входа при разборе проблем с пользователями/магазинами/подписками и при работе с данными.
- `ai-docs/marketplace-auth.md` - авторизация и «активность» магазинов WB/Ozon/Yandex Market (обычный ключ vs OAuth, статусы токенов, условия синка). Точка входа при вопросах о подключении/синхронизации магазинов.
- `ai-docs/design-system.md` - дизайн-система (токены, типографика, отступы, эталонные страницы). ОБЯЗАТЕЛЬНАЯ точка входа перед любой вёрсткой UI (`.vue`/`.scss`). Живой каталог — страница `/design-system` (Foundations + Компоненты `Ds*` + Паттерны); готовые компоненты — `resources/js/Components/Ds/*`; гайд для генерации — `ai-docs/ds-ai-style-guide.md`.
- `ai-docs/queues-and-marketplace-api.md` - воркеры, пулы, очереди и прочее - то как загружается информация по API маркетплейсов.
- `README.md` - запуск проекта, локальное окружение и штатные эксплуатационные команды.

## Актуализация ai-docs — ОБЯЗАТЕЛЬНО при каждом изменении

**Правило:** любое изменение кода/поведения проекта, попадающее в зону ответственности одного из файлов `ai-docs/` ниже, ОБЯЗАНО в том же заходе сопровождаться правкой этого файла. Документация — часть Definition of Done, а не отдельная задача «на потом». Не уверен, задета ли зона — открой соответствующий файл и проверь. Правки — минимально-достаточные и фактические (без выдумок, только то, что реально в коде).

**Карта «что в каком файле → когда обновлять»:**

## Обязательный порядок работы

1. Перед правками определить затронутые модули, очереди, env/config и пользовательские сценарии.
2. Следовать правилам из `ai-docs/arch-rules.md`; если есть конфликт между файлами, приоритет у `CLAUDE.md`/`AGENTS.md`, затем у `ai-docs/arch-rules.md`, затем у `ai-docs/architecture.md`, затем у `README.md`.
3. Актуализировать соответствующий файл `ai-docs/` по правилу и карте из раздела «Актуализация ai-docs — ОБЯЗАТЕЛЬНО при каждом изменении» выше (архитектура/потоки → `architecture.md`, схема БД → `database-structure.md`, авторизация/синк → `marketplace-auth.md`, очереди/API → `queues-and-marketplace-api.md`, конвенции → `arch-rules.md`, UI/токены → `design-system.md`). Это часть Definition of Done.
4. При изменении запуска, установки, Docker, worker-ов, Makefile, Supervisor, тестовых команд или служебных artisan-команд актуализировать `README.md`.
5. При добавлении или изменении переменных окружения актуализировать `.env.example` и локальный `.env`. В `.env` добавлять комментарии: какой доступ нужен и где его найти/получить.
6. Если под задачу есть план/ТЗ в `ai-tz/` — после реализации каждого этапа отмечать его выполненным (`выполнено`), не удаляя сам пункт.
7. Не коммитить и не отправлять в GitHub `.env`, секреты, ключи, токены, дампы с чувствительными данными и временные артефакты.
8. Перед любой вёрсткой UI (создание/правка `.vue`-компонентов и `.scss`) сначала прочитать `ai-docs/design-system.md`, а через него — первоисточники `resources/js/Pages/DesignSystem/Shared/tokens.js` (реестр токенов с правилами применения в поле `note`) и `resources/scss/_variables.scss` (`:root` — канонические значения). Использовать только токены/классы оттуда: цвета — `var(--token)`, отступы/размеры — `var(--size-*)`, радиусы — `--radius-*`, текст — классы `t-*`. Запрещены сырые hex, px вне шкалы `--size-*` и произвольные радиусы. Нет подходящего токена → сначала добавить его в `_variables.scss` и `tokens.js`, затем использовать.

## Git и ветки

- Новую рабочую ветку от `develop` создавать так, чтобы её upstream НЕ указывал на `develop`. Использовать `git checkout --no-track -b <branch> origin/develop` (предварительно `git fetch origin develop`). Не использовать `git checkout -b <branch> origin/develop` без `--no-track` — он назначает upstream = `develop`, и тогда случайный `git push` уходит прямо в общую `develop`.
- Push рабочей ветки делать только явно в одноимённую удалённую ветку: `git push -u origin <branch>`. Никогда не пушить напрямую в `develop` (и тем более в `main`/`master`) без явной просьбы пользователя.
- Коммитить и пушить только по явной просьбе пользователя.

### Production-сервер — строгое правило

На production-сервере (`sellerdata:22`, `/var/www/app.sellerdata.ru/`) НИКОГДА не выполнять никаких изменений без явного подтверждения пользователя в текущем диалоге. Это касается всего, не только БД:

- никаких записей/правок/удалений в БД;
- никаких файлов, в том числе временных (не копировать скрипты/команды/выгрузки, не создавать каталоги, не писать в `/tmp`);
- никаких artisan-команд, миграций, очередей, перезапусков сервисов и т.п.

Read-only обращения (чтение БД через SELECT, чтение файлов/логов) допустимы для диагностики. Любое действие, меняющее состояние прода, выполнять ТОЛЬКО после явного «да» от пользователя на это конкретное действие. Согласие на действие в одном случае не распространяется на следующие.

## Деплой и окружения

Три окружения, разные способы:
- **Локальная разработка** — Docker Compose (см. `README.md`, `docker-compose.yml`). Команды через `docker compose exec app …`.
- **Тест** — `sellerdata-bkp:22`, `/var/www/dev.sellerdata.ru/`. Приложение крутится **на хосте** (не в docker): `php artisan`/`composer`/`vite` запускаются напрямую, воркеры — под supervisor.
- **Прод** — `sellerdata:22`, `/var/www/app.sellerdata.ru/`. Тоже **host-based**, воркеры под supervisor. **Автодеплоя/CI нет** — деплой ручной (`git pull` на сервере).

Общие подводные камни (проверено на практике):
- **Код на серверы (тест/прод) — ТОЛЬКО через git:** закоммитить+запушить ветку → на сервере `git pull`/`checkout`. Прямой `scp`/`rsync` рабочего дерева ЗАПРЕЩЁН (дерево «грязнеет», ветку не переключить без потери WIP, состояние сервера расходится с git). Временные диагностические скрипты — в `/tmp`, удалять за собой.
- **`npm` не в PATH** у SSH-пользователя на серверах. Собирать фронт через `node node_modules/.bin/vite build` (это и есть `npm run prod`). `npm ci`/`npm install` — только если менялся `package-lock.json` (тогда искать доступный npm/node).
- **`composer install`** — только если менялся `composer.lock`. Если просто добавились новые PHP-классы — достаточно `composer dump-autoload -o` (иначе класс может не подхватиться оптимизированным автозагрузчиком).
- **`php artisan queue:restart` ОБЯЗАТЕЛЕН**, если менялся код джобов — воркеры держат старый код до рестарта (симптом: фикс в коде есть, а в логе всё ещё старая ошибка).
- **Не делать `git reset --hard origin/<X>`, стоя на ДРУГОЙ ветке** — это двигает указатель текущей ветки на чужой коммит. Переключаться `git checkout <branch>` затем `git pull --ff-only`.
- Глубина очередей — `Redis::connection()->llen('queues:<name>')`. Статус воркеров — `sudo -n supervisorctl status`. Расчётные воркеры `sd_prod_orders_calculate` умеют молча уходить в FATAL и копить бэклог `orders-calculate` (тогда `redeemed`/статусы заказов не обновляются). Есть алерт `app:monitoring:queue-backlog` (ERROR → Telegram).

### Прод: релиз и деплой (порядок)

Предусловие: чистое git-состояние; всё нужное влито в `develop` (мержить из актуального origin: `git merge --no-ff origin/<branch>`; конфликты `release.sh` не решает — предварительно превьюить merge на временной ветке от `production`).

1. **Релиз (git):** `./release.sh` — переключается на `production`, `git pull`, `merge --no-ff develop`, `git push origin production`, возврат на `develop`. Перед запуском **записать текущий tip `production`** (точка отката).
2. **Деплой кода на прод-сервере** (каждый шаг — по явному «да»):
   - `git pull` (fast-forward);
   - `composer install` (если менялся `composer.lock`) **или** `composer dump-autoload -o` (если добавлены классы);
   - `php artisan migrate --force`;
   - сборка фронта: `node node_modules/.bin/vite build`;
   - `php artisan optimize:clear`;
   - `php artisan queue:restart` (чтобы воркеры взяли новый код).
3. **Проверки:** HTTP 200, свежие `production.ERROR` в `storage/logs/laravel.log`, ключевые фичи.

**Откат кода** (быстрый): revert merge-коммита (`git revert -m 1 <merge>`) или `reset --hard <старый tip> && push --force` в `production`, затем передеплой. Миграции релиза обычно аддитивны (новые таблицы) → откат схемы не нужен. **Данные-мутирующие шаги (валютный ресинк и т.п.) мгновенно НЕ откатываются** — только повторным ресинком; поэтому такие шаги делать ПОСЛЕДНИМИ, уже убедившись, что код-релиз здоров.

### Тест (dev.sellerdata.ru): переключение ветки и пересборка

**ВАЖНО — ветка на тесте пиннится через файл `.branch`, а НЕ ручным `git checkout`.** В корне репо есть файл `.branch` (одна строка — имя целевой ветки). Cron пользователя `developer` КАЖДУЮ МИНУТУ гоняет `./branch.sh`, который приводит рабочую копию к ветке из `.branch` (`checkout` + `pull --ff-only` + `make refresh`). Поэтому ручной `git checkout <branch>` откатывается назад в течение минуты. Чтобы переключить ветку на тесте — **менять содержимое `.branch`**:

1. Записать ветку в файл: `printf "<branch>\n" > .branch` (в корне `/var/www/dev.sellerdata.ru`). Затем сразу применить: `sh branch.sh` (или подождать до минуты, пока сработает cron).
2. `make refresh` внутри `branch.sh`: `npm` нет в PATH у SSH-пользователя (штатно). **С фикса в develop (5063baf6f, `[fix-branch-refresh]`) это больше НЕ роняет refresh** — шаг сборки фронта необрывающий (ведущий `-`): пробует `npm`, иначе фолбэк на `node node_modules/.bin/vite build`, и `php artisan up` выполняется В ЛЮБОМ случае. Т.е. на ветках, содержащих этот фикс (все, что от свежего `develop`), сайт после свитча сам поднимается и фронт собирается через vite-фолбэк.
   - **Старое поведение (ветки БЕЗ фикса, до 5063baf6f):** `php artisan up` стоит в конце `make refresh` ПОСЛЕ `npm ci`/`npm run prod`; npm падает → до `up` дело не доходит → сайт ЗАЛИПАЕТ в maintenance (и на полу-поднятом приложении вылезает, напр., `DecryptException` при чтении зашифрованного `api_key`). Лечение вручную: собрать фронт (`node node_modules/.bin/vite build`), `php artisan optimize:clear`, `php artisan up`. Чтобы фикс попал в старую фичевую ветку — влить в неё свежий `develop`.
   - `make refresh` гоняется только при РЕАЛЬНОЙ смене ветки. Когда `.branch` == текущей ветке — «Already on branch … Nothing to do», `down` не трогается, сайт live. Проверить: `tail /tmp/branch.log`.
3. `composer install` при изменении `composer.lock` (иначе `composer dump-autoload` при новых классах); `php artisan migrate --force` при новых миграциях.
4. `php artisan optimize:clear`; `php artisan queue:restart` при изменениях кода джобов.
5. Если менялись `VITE_*` в `.env` — сначала править `.env`, затем пересобирать. Websocket на тесте: `VITE_PUSHER_HOST=wss-dev.sellerdata.ru`, `VITE_PUSHER_PORT=443`, `VITE_PUSHER_SCHEME=https`.
6. Если приложение застряло в maintenance — `php artisan up`.
7. `production` в `.branch` запрещён (`branch.sh` завершится с ошибкой). Закончив с чужой веткой — вернуть `.branch` в исходное значение, иначе тест «залипнет» на ней.

Тестовый режим оплаты на тесте (bypass) — тоже через `.env`: `AUDIT_PAYMENT_BYPASS` и `HISTORICAL_LOAD_PAYMENT_BYPASS` (`true`/`false`), после правки — `php artisan optimize:clear`.

### Локально (Docker Compose): после `git pull`/переключения ветки

### Пост-релизные операции (по потребности фичей)

- **Валюта магазина (RUB→KZT и т.п.) — строгий порядок:** выставить `accounts.currency` → `php artisan queue:restart` (сброс статического кеша валюты в воркерах) → `php artisan app:accounts:sync-date <id> --date-from=<start> --date-to=<сегодня>` → проверка (retail ~×6, `failed_jobs`=0, покрытие дат, суммы в валюте). Ресинк тянет данные маркетплейса заново; ручные данные (себестоимость, расходы, самовыкупы) не трогает. Если ресинк до рестарта — часть данных ляжет в старой валюте.
- **Разбор зависших реклама-джоб:** `php artisan app:expenses:reset-failed --max-attempts=<N> --limit=<M>` возвращает транзиентные `failed` (`expense_job_controls`) в `pending`. Строки с `attempts >= max-attempts` штатный крон (`--max-attempts=5`) не трогает — их поднимать бОльшим `--max-attempts`. Делать, когда БД без высокой lock-нагрузки.
- **Ускорить разгребание очереди безопасно:** транзиентные воркеры `setsid nohup php artisan queue:work --queue=<name> … &` (PID сохранить). Откат — `kill` PID (и они гаснут на ближайшем `queue:restart`), конфиг supervisor не трогается. Следить за lock-timeout: если контеншн растёт — убрать лишние воркеры.
